## F107 / F109 — дублирующаяся family-запись (P310 ↔ P174)

`tree-fallback.json`: `F107` и `F109` — две отдельные family-записи для
**одной и той же** супружеской пары (husband=P310, wife=P174 в обеих):

```
F107 = { husband: "P310", wife: "P174", children: [] }
F109 = { husband: "P310", wife: "P174", children: ["P101"] }
```

Это не повторный брак и не полигамия — husband/wife совпадают полностью.
Похоже на случайное дублирование записи при ручном/автоматическом
редактировании дерева (одна пустая, другая с ребёнком).

  удалить дублирующую (пустую) запись;
- сделать это через `admin.html` → «Загрузить дерево» после ручной правки
  JSON, либо через прямой `PATCH`/`DELETE /api/family/:id` (см.
  `src/index.js`), а не редактированием layout-алгоритма — сам алгоритм
  раскладки (`tree-print-layout3.js`) корректно отражает то, что задано

## 29 наложений карточек в placeFamiliesInRow() (ветка onePlaced) — known limitation

**Статус: known limitation, не критично для текущего использования.**

Визуальный аудит `layoutAllComponents()` на всех 239 персонах / 41 компоненте
выявил 29 случаев, где карточка из ветки onePlaced (супруг(а), чья позиция
вычисляется от уже размещённого «владельца») пересекается (`|x1-x2| < CW`
на одном `y`) с уже размещённой extern-позицией — соседом из children-block
предыдущего row или другой семьи на том же row.

Три независимые попытки фикса (глобальный row-floor через `occupiedRightEdge`,
точечная pre-sweep проверка коллизии, anchor-check внутри существующего
sequential prevRight-прохода) — каждая полностью устраняла все 29
пересечений, но при этом создавала каскадную регрессию: 24+ новые пары
с большим разрывом (`gap>300`) там, где раньше стояла корректная пара
вплотную (`gap=12`, `COUPLE_GAP`). Причина — структурная: `prevRight` в
едином проходе `placeFamiliesInRow` накапливается **последовательно через
весь row**, и любой локальный сдвиг одной задачи вправо (чтобы закрыть её
конкретное пересечение) автоматически сдвигает `prevRight` для **всех**
последующих задач этого же вызова, даже если у них самих не было
пересечения ни с чем. На многолюдных row (например, 130-персонная
компонента) это превращает один точечный фикс в цепную реакцию.

**Требуется** для полноценного исправления: алгоритм компакции по
кластерам (union-find/graph-based — сначала выявить независимые
«островки» задач на row, устранять пересечения ВНУТРИ каждого острова
отдельно, не давая сдвигу одного острова влиять на другие), а не точечный
патч поверх текущего однонаправленного sweep. Это отдельная, более крупная
задача по перепроектированию `placeFamiliesInRow`/`placeChildrenOfFamiliesInRow`,
не входит в scope точечных фиксов.

См. комментарий `KNOWN LIMITATION` в шапке `placeFamiliesInRow()` в
`tree-print-layout3.js`.
